# Dual release acceptance

The onboarding and release changes retain TapeOut's mandatory numerical authorization and GenLayer's finalized semantic review. X Layer 1952 remains the existing testnet VM adapter. Official CPU registration belongs to X Layer 196 and must be proven by its official registry and actual receipts. Both payment deployments continue to use GenLayer Studionet 61999, which is testnet simulator infrastructure.

Run `node tools/production/verify-acceptance.mjs` for the local application, contract, report, bridge-proof and recovery controls. Its success token means those local checks passed. It does not prove live validator reliability, mainnet payments, a registered CPU, operational fault injection, or availability.

| Scenario | Local decisive controls | Required live evidence |
|---|---|---|
| Permitted purchase | Exact policy/request/evidence hashes; finalized approval; all criteria pass; unique Paid and exact Transfer | At least ten new delivered payments in each round, independently checked against source RPC receipts |
| Prohibited purchase | Finalized REJECT; no settlement; reservation released | At least ten finalized rejections per round; cancellation cannot replace rejection |
| Prompt injection | Owner mandate and evidence remain immutable; unsafe approval and incomplete criteria fail | At least ten fresh injection cases per round with the declared terminal outcome |
| Buyer/evidence mismatch | Contradictory buyer, amount, expiry, hash and source are rejected before reserve or review | At least ten fresh cases in the combined buyer/hash group per round |
| Numerical limits | TapeOut blocks before fetching evidence or submitting consensus; boundary/fuzz comparisons use the real VM | Budget block with skipped review and no payment in every round; official CPU vectors verified separately |
| Consensus failure | Terminal failure persists cancellation, releases reservation and stops retrying; no attestation | Failed consensus control in every round, with its actual review stage and deadline |
| Authorization races | Owner, key, chain, token, settlement, reviewer, snapshots and worker lease are rechecked after asynchronous finality | Pause/resume, key rotation/revocation and emergency pause receipts and traces |
| Crash/outage recovery | Reservation, signed intent, burn, mint, acknowledgement and completed payment recover without duplicate execution | Fault injection before reserve, after reserve, burn, mint and acknowledgement; outage recovery and idempotent retry traces |
| Bridge proof | Exact source message and events; Circle attestation signatures; confirmed destination MessageReceived and mint; nonce consumption; typed acknowledgement and source BridgePaid | Captured proof and independently refetched source/destination/acknowledgement receipts, with recipient/amount/domain/source/hash checks |
| Forged proof/attestor | Mutated acknowledgements, replay, wrong attestor and missing/duplicate mint fail; pause remains available | Actual altered-proof and forged-acknowledgement controls; report the remaining immutable-attestor trust boundary |
| Legacy reviewer | V1 source SHA256 remains `0ec8749a19725514590989989645671f8211c346d78e68e3c9bf18866a3585b4`; old policies, balances, reservations and history stay intact | Testnet owner explicitly replaces a legacy card, verifies the new reviewer/policy, rotates credentials and transfers available funds; mainnet rejects copied legacy clients and credentials |

Use two independently generated fixtures and reports for **each** payment environment. Every case needs a new invoice identifier and request ID. Repeated inputs, reused request IDs, one run presented twice, source/environment drift, missing scenarios, optimistic latency summaries, or unsafe cases marked PAID fail qualification. The evidence must follow deployment of the exact release and be no older than seven days when qualified.

The existing live runner is `scripts/audit-production-semantic.ts`. Its thresholds are fixed before execution: queue p95 ten minutes, local settlement p95 thirty minutes, CCTP p95 sixty minutes, cancellation p95 ten minutes, maximum completion seventy minutes, and a thirty-minute pre-burn deadline. Admission is bounded to thirty seconds. Wall and monotonic clocks must agree within one second; saved server timestamps allow thirty seconds of observation skew. Reports preserve the first observed state and review-stage transitions, admission/completion times, and before/after source ledgers. The qualifier recomputes latency and independently compares the saved input and request timestamps with authenticated and public records. Admission, approval, a burn, or a Circle attestation is never credited as delivered payment.

The ledger's `funded` field is the current physical token balance. A delivered payment must debit `funded` and `available` by its exact amount, increase cumulative `spent` by that amount, and release the case's reservation. Unsafe cases must show no debit or spent increase, and independent source reads must show an absent or cancelled reservation. Both direct settlement and CCTP burn debit the source balance; PAID-only display usage credits a bridge only after recipient delivery and acknowledgement. Extra deposits, withdrawals or concurrent operations invalidate this isolated measurement and need an operator review before a new audit.

Finalized reviewer source, constructor policy and settlement, review calldata, evidence snapshots, complete criteria and stored result are read directly from Studionet. The API's finality marker alone does not qualify. CCTP proof checks independently decode the actual source acknowledgement transaction and recover its typed-data signer against the immutable attestor, as well as checking burn/message, Circle signatures, mint, nonce consumption and exact recipient delivery. Older reports without these measurements remain historical and cannot qualify the new release.

`scripts/acceptance-report.mjs verify <manifest.json> [report.json]` requires a version1 `dual-release-live-acceptance` manifest with both releases. Each release binds `paymentEnvironment`, `chainId`, `sourceCommit`, `releaseId`, canonical `applicationOrigin`, `deployedAt`, and `allowedTokens`. Its two `rounds` contain hash-pinned `reportPath`, `reportSha256`, `fixturePath`, and `fixtureSha256`. Private original request inputs are refetched with the separate `INTENTGUARD_TESTNET_AUDIT_AGENT_KEY` or `INTENTGUARD_MAINNET_AUDIT_AGENT_KEY`. These credentials stay in the process and are excluded from reports.

Physical fault injection, HTTP denial traces, and explicit legacy fund transfer require operator review of the actual run. Record that review in a hash-pinned `operationalReviewPath` and `operationalReviewSha256`, with kind `reviewed-live-operational-evidence`, release identity, `reviewedBy`, `reviewReference`, and each named scenario's actual evidence path/hash. The report explicitly distinguishes this review from automatic public-receipt verification. Never create a passed review from local fixtures or a planned operation. Preserve balances, reservation commitments, owner signatures and exact request/receipt IDs in the reviewed evidence, with credentials and raw signed transactions redacted.

The attestor remains immutable and trusted to acknowledge foreign-chain delivery. X Layer has no foreign-chain light client. Rotation of an agent API key does not rotate the attestor. Emergency pause and safe recovery reduce operational risk; they do not remove that trust boundary. This is scoped testing and evidence verification, not formal verification or a third-party audit.

Actual live rounds and operational acceptance remain pending until current executions and evidence exist. Historical 10/12 and later 8/8 testnet audits remain unchanged.
